# Melisle 乐岛移动端设计审计

审计日期：2026-09-09

## 审计范围

- 产品：Melisle 乐岛 Flutter 移动端
- 核心任务：首页发现与继续聆听 → 媒体库浏览 → 播放歌曲
- 证据：本轮从正在运行的 iPhone 17 / iOS 26.5 模拟器重新捕获的首页、媒体库和播放器截图
- 模式：UX、视觉与可访问性联合审计

## 总体判断

当前移动端的基础结构是健康的：页面归属清楚、五项底部导航稳定、媒体库分类直接、播放器任务完整。主要问题不在功能布局错误，而在于视觉语言仍偏通用、音乐内容与操作之间缺少更有辨识度的节奏，导致界面“能用但不够精细”。

## 逐步审计

### 1. 首页发现与继续聆听 — 一般，有明显提升空间

证据：`01-home-clean.png`

优点：首屏标题、推荐、最近播放和底部导航层级明确；真实封面能快速建立内容感；主要区域触达面积充足。

问题：推荐卡更像通用模板而不是音乐产品的品牌时刻；首屏没有清晰呈现“当前正在听什么”；大标题、推荐卡、最近播放之间的节奏较松散，但内容重点仍不够突出；推荐卡的装饰图形与真实专辑内容联系弱。

机会：将“继续播放”或“为你发现”明确为唯一首要任务；用专辑封面、曲目进度或策展文案建立更强的音乐叙事；减少模板式大卡，强化版式、文字和封面之间的关系。

### 2. 媒体库歌曲浏览 — 良好，但偏工具化

证据：`02-library-songs-clean.png`

优点：搜索、四分类切换和歌曲列表的任务顺序合理；时长与更多操作保持稳定对齐；单页信息密度足以服务大型曲库。

问题：搜索框与分类控件占据较多首屏高度；列表缺少封面或更有层次的当前播放反馈，连续浏览时视觉锚点不足；序号、标题、元信息、时长和菜单都使用相近的视觉力度；乱码、超长元数据和单行截断会放大“不精致”的感受。

机会：压缩顶部控制区，将筛选融入更轻量的模式；建立标题、艺术家/专辑、时长的更精确层级；为当前播放、下载或高音质状态提供克制但可辨识的行内反馈；优先治理异常元数据的展示策略。

### 3. 全屏播放器 — 任务完整，但品质过度依赖封面

证据：`03-player-clean.png`

优点：封面、歌曲信息、歌词/空态、进度和播放控制顺序符合预期；主播放按钮突出；底部收藏、音量和音质有可见文字，不完全依赖图标猜测。

问题：大面积背景取色和超大封面会放大低质量、广告化或构图不佳的源封面；“暂无歌词”区域留白很大，却没有提供有意义的替代内容；播放模式、上一曲、下一曲和队列的视觉权重较接近；页面上下区域的纵向节奏略显松散。

机会：为低质量封面建立降噪、裁切或弱化策略；无歌词时显示专辑信息、下一首或简洁的声场视觉；把主控制和次级控制分层；让背景氛围服务内容，而不是直接复制封面缺陷。

## 跨页面问题

1. 视觉身份偏弱：绿色、圆角和 Material 图标形成一致性，但还不足以让用户一眼认出“乐岛”。
2. 层级依赖字号和容器：细节层级、对齐、分隔和状态表达仍可更精确。
3. 首页与播放器割裂：首页偏浅色内容目录，播放器偏封面取色沉浸，缺少贯穿两者的品牌节奏。
4. 极端内容质量缺少保护：乱码、超长标题、异常封面会显著拉低整体观感。
5. 可访问性仍需动态验证：截图可以确认可见标签和大致触达面积，但不能证明 VoiceOver 顺序、动态字体 2.0 倍、减少动态效果或完整对比度合规。

## 优先级建议

1. 先重构首页的主任务和播放器的内容层级，建立一套贯穿浏览与播放的视觉母题。
2. 再统一列表、导航、状态和元数据的精细规范，减少通用控件感。
3. 最后覆盖异常封面、乱码、超长文字、无歌词、加载和错误等真实数据边界。
4. 实施前补做 390×844 深色模式、2.0 倍动态字体和 VoiceOver 走查。

## 证据限制

本轮只覆盖浅色主题下的首页、媒体库歌曲列表和全屏播放器；未覆盖登录、搜索结果、详情页、Bottom Sheet、深色模式、横屏、软键盘、2.0 倍字号、VoiceOver 和网络错误，因此不能据此声明完整无障碍合规。
