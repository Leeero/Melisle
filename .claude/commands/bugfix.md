执行 **Bug 修复工作流**，问题：$ARGUMENTS

使用 TaskCreate 为每个阶段创建任务，完成后标记 completed。

## 阶段 1：问题分析

角色：**编排器/产品经理**

- 收集错误信息、复现步骤、环境信息
- 分析错误表现和影响范围
- 分类问题类型

**问题分类**：
- **崩溃** — 应用闪退、未捕获异常
- **功能异常** — 行为不符合预期
- **UI 问题** — 布局错乱、动画异常、响应式问题
- **性能** — 卡顿、内存泄漏、慢请求

**输出格式**：
- 问题描述
- 复现步骤
- 预期行为 vs 实际行为
- 影响范围
- 问题分类

## 阶段 2：根因定位

角色：**开发者**

- 定位相关代码位置
- 分析逻辑和数据流
- 识别根本原因
- 确定修复方案

**按问题类型的分析重点**：
- 崩溃 → 异常处理、空值检查、边界条件
- 功能异常 → 业务逻辑、状态管理、数据流
- UI 问题 → 布局、动画、响应式、`design.md` 规范
- 性能 → 算法复杂度、内存使用、网络请求

**输出格式**：
- 问题定位：文件路径 / 方法名 / 行号
- 根本原因描述
- 修复方案
- 影响评估
- 回归风险

**检查清单**:
- [ ] 代码位置已定位
- [ ] 根本原因已识别
- [ ] 修复方案已确定
- [ ] 影响评估已完成
- [ ] 回归风险已识别

## 阶段 3：修复实现

角色：**开发者**

- 实施最小化修复
- 添加防御性代码（如适用）
- 保持代码风格一致

**修复原则**：
- **最小化修改**：只修改必要的代码
- **保持兼容**：不破坏现有功能
- **添加注释**：复杂修复添加说明
- **防御性编程**：添加边界检查

**检查清单**:
- [ ] 修复代码正确
- [ ] 最小化变更
- [ ] 无副作用引入
- [ ] 代码风格一致
- [ ] 必要注释已添加
- [ ] 通过 `flutter analyze`

## 阶段 4：回归测试

角色：**测试者**

- 验证问题已解决
- 运行相关回归测试
- 测试边界条件
- 测试相关功能

**测试范围**：
- **直接测试**：直接测试修复的问题
- **回归测试**：测试可能受影响的功能
- **边界测试**：测试边界条件

**检查清单**:
- [ ] 原问题已修复
- [ ] 相关测试通过
- [ ] 无新问题引入
- [ ] 边界条件正常

## 阶段 5：代码审查（自审）

角色：**审查员**

- 检查修复代码质量
- 验证修复方案合理性
- 更新相关文档（如需要）

**检查清单**:
- [ ] 修复方案合理
- [ ] 代码质量良好
- [ ] 注释完整
- [ ] 文档已更新（如需要）

## 阶段 6：提交修复

角色：**开发者**

依次执行：
1. `dart format lib/`
2. `flutter analyze`
3. `flutter test`
4. 提交代码：`fix(<scope>): <subject>`

Scope 选项：player / auth / library / ui / network / repository / settings

**检查清单**:
- [ ] 代码已格式化
- [ ] 无 lint 错误
- [ ] 所有测试通过
- [ ] 提交信息规范（Conventional Commits）
- [ ] 分支命名正确（`fix/<issue-number>-<brief>`）

## 严重程度处理指引

| 级别 | 响应时间 | 测试范围 |
|------|---------|---------|
| Critical（崩溃/数据丢失） | 立即 | 最小化测试，快速修复 |
| High | 1小时内 | 完整测试 |
| Medium | 1天内 | 完整测试 |
| Low | 1周内 | 完整测试 |
