以**产品经理**视角分析需求：$ARGUMENTS

## 执行步骤

### 1. 读取背景资料

- `.codebuddy/knowledge/prd.md` — 现有功能全景、竞品分析、非功能需求
- `.codebuddy/knowledge/roadmap.md` — 版本路线图（v1.1 ~ v3.0）
- `.codebuddy/knowledge/architecture.md` — 技术架构约束

### 2. 需求分析

从用户目标和现有代码倒推真实功能范围：

- **功能目标**：一句话定义核心价值
- **目标用户画像**：
  - A: 自托管发烧友（30-45岁，NAS/VPS，FLAC/DSD，高要求）
  - B: 数字收藏家（25-40岁，追求所有权，重歌单管理）
  - C: 极简主义者（干净UI，深色模式，沉浸聆听）
- **用户场景**：具体的使用场景列表
- **与现有功能的关系**：是新增、增强还是修改

### 3. 范围定义

- **本次包含**：明确列出要做的功能点
- **本次不包含**：明确排除的功能点
- **技术约束**：
  - 不破坏 MusicRepository 单一抽象
  - 不引入反向依赖
  - 跨端一致性

### 4. 竞品参考

结合 PRD 中的竞品分析（Plexamp / Finamp / Symfonium），说明：
- 竞品如何实现类似功能
- 乐岛的差异化方向
- 不照搬竞品功能，结合自托管场景

```

- <排除项>

- [ ] <可测试的完成条件>

### 竞品参考

|------|---------|---------|
| ... | ... | ... |

### 技术依赖
- <依赖项>

### 优先级建议
<结合路线图的优先级建议和版本归属>

- <技术风险>
- <产品风险>
```

## 约束

- 以当前代码和项目文档为事实来源，不臆造功能状态
- 不照搬竞品功能，必须结合自托管场景
- 验收标准必须可交给开发/测试执行
- 产品方向：精致、克制、沉浸、统一
